### 一言で（ピッチ用）

> 「ベンチはある。でも座れる？ 日陰？」— カメラもセンサーもなしで、AI が"今座れるベンチ"を教える休憩マップ。

## 2. デモシナリオ（このとおりに動けば MVP 完成）

💡 提案。審査員の前で 2 分以内に見せる流れです。

1. **8月の14時、みなとみらいで疲れた学生**がアプリを開く（現在地はみなとみらい）
2. マップに近くの休憩スポット（ベンチ・トイレ・ゴミ箱・水飲み場）がピンで出る。ベンチのピンは **空席確率で色分け**（緑＝座れそう／黄／赤＝埋まってそう）
3. 「日陰のみ」で絞り込むと、**14時に日陰になっているベンチだけ**が残る
4. ベンチをタップ → 詳細カード
   - 🤖 **AI予測: 空席確率 72%**（理由: 「平日昼・日陰・駅から離れている」）
   - 👥 **みんなの投稿: 12分前「座れた」**（AI予測とは別枠・別アイコンで表示）
   - 🌳 **時間別日陰**: 時刻スライダーを動かすと、建物の影が地図上で動く（10時は日なた → 14時は日陰）
5. 「ここへ行く」→ **アプリ内に徒歩ルートを表示**（Google マップアプリには飛ばない）
6. 着いたら「座れた／満席だった」をワンタップ投稿 → その場で表示が更新される（**使うほど賢くなるループ**）

## 4. コア機能のロジック

### M3 空席確率（💡 提案・カメラ／センサーなし）

議事録では「何を入力にするか」が決まっていないので、たたき台を置きます。

**入力（すべて公開データ or 端末内で手に入るもの）**

| 要素 | 例 | 効き方 |
| --- | --- | --- |
| 時間帯・曜日 | 平日14時、休日12時 | 昼休み・休日昼は埋まりやすい |
| 天気・気温 | 晴れ32℃ | 暑い日は**日陰のベンチから**埋まる |
| 日陰状態（M2の結果） | 14時は日陰 | 日陰 × 暑い日 → 混む |
| 周辺施設までの距離 | 駅・商業施設・観光地から何 m か | 近いほど人が多い |
| イベント | 赤レンガのイベント開催日 | 近くのイベントで混雑（No.10 を簡易に取り込む） |
| 席数 | ベンチ 1 台あたり何人座れるか | 席が多いほど空きやすい |
| みんなの投稿（M4） | 12分前「座れた」 | 新しいほど強く効き、時間がたつと AI予測に戻る |

**計算**

- **デモモード（API なし）**: 上の要素に重みを付けたルールベースのスコア → 0〜100% に変換。式と重みは `config` に置いて、チームで調整できるようにする
- **API モード**: Gemini に要素を渡して確率の補正と「理由の一文」を生成させる。Gemini が落ちたときはデモモードの値をそのまま使う
- 投稿があった場合: `表示確率 = AI予測 × (1 − w) + 投稿 × w`（w は投稿の新しさで 1 → 0 に減る。例: 30分で半分）

**見せ方のルール（✅ 議事録）**: AI予測（🤖）とみんなの投稿（👥）は**必ず別枠・別アイコン**で表示し、混ぜて 1 つの数字だけを見せない。

### M2 時間別日陰（💡 提案）

- **デモモード（API なし）**: **作成済みの建物データ 1274 件**（建物の形と高さ）と、日時から計算した太陽の位置（方位・高度）を使い、建物の影を地図上に描く。ベンチが影の中に入っているかで「日陰／日なた」を判定する。太陽位置の計算はライブラリ（例: SunCalc）でできるので **API 不要**
- **API モード**: Google の 3D データ（Photorealistic 3D Tiles または Solar API。どちらにするかは調査中）で精度を上げる。木の陰はデモモードではスポットの「木陰あり」フラグで代用する
- 時刻スライダーは 7:00〜18:00 を 30 分刻み

### M6 アプリ内ルート

- **デモモード**: 直線＋おおよその徒歩時間（距離 ÷ 80m/分）
- **API モード**: Routes API（または Maps の Directions）で実際の徒歩ルートを描く

## 5. API なしモード ↔ API モード

| 機能 | API なし（デモモード） | API あり | 使う API |
| --- | --- | --- | --- |
| 地図 | OpenStreetMap タイル（💡） | Google マップ | Maps JavaScript API |
| スポットデータ | 同梱の JSON（みなとみらい分） | ＋Firestore の投稿 | Firebase |
| 日陰 | 建物 1274 件＋太陽位置で計算 | 3D データで精度アップ | 3D Tiles / Solar API（調査中） |
| 空席確率 | ルールベース | Gemini で補正＋理由生成 | Gemini API |
| 天気 | 固定値（デモ用に「晴れ32℃」など切替可） | 天気 API | 💡 未定 |
| 投稿 | 端末内に保存（localStorage） | Firestore で全員に共有 | Firebase |
| ルート | 直線＋推定時間 | 実ルート | Routes API |

`.env` の各キーが空なら、その機能だけ自動でデモモードに切り替わる（✅ 議事録の方針）。予算は約 20 ドルなので、Google Cloud 側で各 API の上限を必ず設定する。

## 6. データ（MVP で用意するもの）

| データ | 件数の目安 | 作り方 |
| --- | --- | --- |
| 休憩スポット | 💡 30〜50 件（みなとみらい） | 現地確認＋地図から手入力。**一次情報として現地で写真を撮る**（審査の原則） |
| 建物 | 1274 件 | ✅ 作成済み（#21） |
| 周辺施設・駅 | 💡 10〜20 件 | 手入力 |
| イベント | 💡 2〜3 件 | デモ日に合わせた仮データ |

スポットの持つ項目（💡）: `id, name, type(bench/toilet/trash/water/roof), lat, lng, seats, hasRoof, hasTreeShade, photo, tags(季節など), source(現地確認/外部データ)`

投稿の持つ項目（💡）: `spotId, status(sat/full), createdAt, (匿名ID)`

## 7. 技術構成（💡 提案・要合意）

| 項目 | 提案 | 理由 |
| --- | --- | --- |
| アプリ形態 | **Web アプリ（PWA）を 1 本作り、APK は同じコードを包んで出す**（例: Capacitor） | ✅ 議事録「APK＋Web」を 1 つのコードで満たせる。iPhone の人は Web 版を開ける |
| フロント | React（または Next.js）＋地図ライブラリ | AI でのコード生成と相性が良い。メンバーが慣れているものがあればそちらを優先 |
| 地図 | デモ: Leaflet＋OSM／API: Google Maps | API なしで動かすため |
| 日陰計算 | フロントで計算（SunCalc＋建物データ） | サーバー不要で速い |
| バックエンド | Firebase（Firestore・匿名ログイン・Hosting） | △ 議事録（#14 で候補） |
| AI | Gemini API | ✅ 議事録 |

> 議事録では実装技術（Flutter／React Native／PWA など）が未定です。メンバーが既に作っているプロトタイプ（35機能を試せるもの・#21 の日陰 UI）の技術に合わせるなら、そちらを優先してください。
