# Rest Care — 追加機能と MVP（v0.2 たたき台・2026-11-09）

企画書「Rest Care — 休む場所だけでなく、休むきっかけも届ける」（医療・福祉 × 休憩。**最新版＝Google Health・3D 地図版**）を、いまの `app/`（v0.2〜v0.3）に載せるための計画です。
企画書にあることは「📄 企画書」、企画書にない部分を埋めた案は「💡 提案」と書いています。💡 はチームで合意したら ✅ に変えてください。

> **これまでの [mvp.md](mvp.md) との関係**
> mvp.md の軸は「近くのベンチに今座れるか（日陰か）」。Rest Care はその上に **「休むきっかけ」と「自分に合った場所」** を足します。
> 3D・日陰・空席確率・投稿・徒歩ルートはそのまま土台として使い、作り直しません。
> ⚠️ mvp.md では **バリアフリーを Won't** にしていましたが、企画書では **016 バリアフリーマップが必須** です。どちらで行くかをチームで決めてください（本書は企画書どおり必須として書いています）。

## 2. デモシナリオ（このとおりに動けば MVP 完成）💡

📄 企画書 3章「想定する利用シーン」を、2 分で見せる流れにしたもの。

1. 授業のあと、学生が「休憩する」を押す
2. **いまの状態を 3 タップで入力**：疲れ具合（少し／かなり／限界に近い）・歩いた時間（〜15分／〜30分／30分以上）・希望（涼しい場所・座りたい・トイレ近く・段差なし など）
   - 「限界に近い」を選ぶと、提案より先に **安全の案内**（RC-7）が出る
3. **候補が順位付きで 3 件** 出る。各候補に「徒歩 3 分・冷房あり（確認済み）・空席 70%（推定）」と **理由** が付く
4. 候補をタップ → **詳細カード**。条件ごとに「確認済み／推定／未確認」と **情報源・更新時刻** が並ぶ
5. 「ここへ行く」→ アプリ内の徒歩ルート（既存）
6. 着いたら **1 タップでフィードバック**：「座れた」「満席だった」「設備が使えなかった」→ その場で表示が更新される
7. （追加）歩き続けていると「30分歩いています。近くに日陰のベンチがあります」とアプリ内バナーで休憩を提案（RC-5）

## 4. 追加する機能（Issue 単位）

マイルストーン「Rest Care MVP」に登録済みです（RC-0〜RC-7 は #4〜#11、RC-8 は #14、RC-9 は #15）。

### RC-0（#4） 冷房・屋内休憩スポットのデータ（必須の前提）

- **型**：`Spot` に `cooling: TriState`、`stepFree: TriState`、`accessibleToilet: TriState`、`openHours?: string`、`verifiedAt?: string`（現地確認した日時）、`infoSource`（`osm` / `field-check` / `official` / `user`）を足す。`SpotKind` に `indoor`（屋内休憩所）を足す 💡
- **データ**：みなとみらいの屋内休憩所（公共施設のロビー・クーリングシェルター等）を 10〜20 件、手入力で `app/public/data/` に追加。出典 URL と確認日を必ず持つ 💡
- **互換**：`src/lib/storage.ts` の `validateSaved` で古い保存データ（新項目なし）も読めるようにする。未設定は `unknown`
- **完了条件**：新しい種類が地図と一覧に出る／古いバックアップを復元できる／テスト追加

### RC-1（#5） いまの状態の入力（休憩ニーズ）

- 「休憩する」ボタン → シートで 3 項目を選ぶだけ（自由入力なし、健康情報は端末から出さない）
  - 疲れ具合：少し／かなり／限界に近い
  - 歩いた時間：〜15分／〜30分／30分以上（RC-5 の計測値があれば初期値に）
  - 今日の歩数・活動時間（任意）：おおよその値を選ぶ。RC-8 で Google Health につながっていればその値を初期値にする
  - 希望：涼しい場所・日陰・屋根・座りたい・背もたれ・トイレ近く・段差なし・給水（複数選択）
- 型は `src/domain/restNeed.ts` の `RestNeed`。歩数などには **出どころ（`manual` 手入力／`demo` デモ値／`health` Google Health）** を持たせ、画面に「手入力」「デモ値」「Google Health」と出す（📄 企画書 16章 MVP-2 の完了条件）
- 保存は端末内のみ（前回の希望を初期値にする）
- **完了条件**：3 タップ以内で候補表示まで進める／再読み込み後に前回の希望が残る

### RC-2（#6） 条件別検索の拡張（バリアフリーを含む）

- 絞り込みに **冷房・座席・背もたれ・段差なし・多目的トイレ・給水** を追加（`src/domain/seat.ts` の既存フィルターに並べる）
- 条件ごとに **必須（満たさない地点は除外）／できれば（順位に効く）** を切り替えられる 💡
- 値が `unknown` の地点は、必須条件でも「未確認」として **除外せず下位に残し**、断定しない表示にする（📄 企画書 8章）
- **完了条件**：各条件のテスト／「段差なし」を必須にしても未確認の地点が「利用可能」と表示されない

### RC-3（#7） 休憩候補の順位付け（中核）

- `src/domain/restRank.ts` に純粋関数 `rankRestSpots(spots, need, context)` を作る。**ルールベースで、同じ入力なら必ず同じ順位**（既存の空席確率と同じ方針。Gemini には計算させない）
- スコアの材料 💡

  | 要素 | 中身 | 効き方 |
  | --- | --- | --- |
  | 距離 | 徒歩時間（`route.ts`、つながらなければ直線） | 疲れているほど遠い候補を強く減点（例: 少し=15分まで、かなり=8分まで、限界に近い=5分まで） |
  | 条件の充足 | RC-2 の「できれば」条件を満たした数 | 確認済み > 推定 > 未確認 |
  | 暑さ×日陰 | `wbgt.ts` と `ShadeEngine` の日陰3段階 | 暑い時間は冷房・日陰を加点、日なたを減点 |
  | 座れるか | `SeatPrediction.combined` | 座りたい人には大きく効く |
  | 活動量 | RC-1／RC-8 の歩数・活動時間 | 多いほど「近い・座れる」候補を少し優先。**歩数だけで疲れや体調を判定しない** |
  | 情報の鮮度 | `verifiedAt`・直近の投稿 | 古い／「使えなかった」投稿があれば減点 |

- 戻り値は「点数」だけでなく **理由の材料（`reasons: {key, label, status: 'confirmed'|'estimated'|'unknown'}[]`）** を持つ。RC-4 がそれを表示する
- **完了条件**：上位 3 件と理由が出る／重みは 1 か所にまとめる（`SEAT_MODEL` と同じ書き方）／境界値のテスト

### RC-4（#8） 理由と情報源・更新状況の表示

- 候補カードと詳細に、条件ごとの行を出す：`冷房 あり ✅ 確認済み（現地確認 11/8）`、`空席 70% 🤖 推定（ルール v0）`、`段差なし ❔ 未確認`
- 予測値（🤖）と実測・投稿（👥）・確認済みデータ（✅）を **アイコンと文言で区別**（既存の AI予測／投稿の区別を広げる）
- Gemini（任意）：`/api/explain` を拡張し、RC-3 の `reasons` から **一言の提案文** を作る。プロンプトで「与えた理由以外の設備・数値を書かない」「医療的な判断をしない」を指示し、キーなしでは定型文にする
- **完了条件**：キーなしでも理由と情報源が全部出る／Gemini の文に入力にない設備名が出ないことをテスト（禁止語・未知の設備のチェック）

### RC-5（#9） 休憩のきっかけ（アプリ内の提案）— 追加

- 「歩行モード」を開始した時間（または RC-1 の申告）と、気温・暑さの参考指数から、アプリ内バナーで休憩を提案する
  - 例：30 分以上 ／ 暑さの参考指数が高い時間帯は 20 分で提案 💡
- 「今はいい」で 15 分は再提案しない。「提案を出さない」設定も用意
- **やらないこと**：プッシュ通知・バックグラウンド計測・歩数や健康データの取得（📄 企画書で将来扱い）
- **完了条件**：提案の受け入れ／却下を端末内に記録（📄 企画書 9章「提案の受容率」の測定に使う）

### RC-6（#10） 休憩後のフィードバックを広げる — 追加

- 既存の「座れた／満席／見当たらない」に **「設備が使えなかった」（冷房が止まっていた・閉まっていた・トイレ使用不可 など）** を追加
- `SeatReportValue` を増やすか、別型 `FacilityReport` にするかは実装時に判断（`validateSaved` の互換を優先）
- 投稿は RC-3 の鮮度に反映。Firebase 共有は既存のタスク（TEAM_HANDOFF の P0）に乗せる
- **完了条件**：投稿するとその場で候補の順位・表示が変わる

### RC-7（#11） 安全・信頼性の表示（横断）

- 「限界に近い」を選んだとき：休憩提案より先に「無理に移動せず、近くの人や施設スタッフに声をかける／救急相談窓口に相談する」案内を出す。**窓口の名称・番号は公式情報で確認してから載せる**（未確認のまま載せない）
- アプリ全体の注記：「医療診断・熱中症の危険度判定には使えません」。暑さの参考指数は「参考値」の表記を続ける
- 位置情報は許可があるときだけ使う（既存）。疲労感の入力は端末の外に送らない
- **完了条件**：上の文言が画面にある／疲労感がネットワーク送信に含まれないことを確認（`/api/explain` の送信内容のテスト）

### RC-8（#14） Google Health API との接続（挑戦）— 追加

- 📄 企画書 10〜13章。**MVP は RC-1 の手入力で成立させ、これは挑戦枠**
- `app/server/` に OAuth の入口（開始・コールバック）を足し、トークンはサーバー側だけで持つ。Cloud Run に載せる
- 読むのは **今日の歩数と活動時間だけ**（最小の読み取り権限）。睡眠・心拍は将来
- 端末に返すのは集約した値（今日の歩数など）だけ。**健康データは保存しない・Gemini に送らない**
- 同意画面の前に「何に使うか・保存しないこと・接続の解除方法」を出す
- 本人のテストアカウントでだけ試す。一般公開には OAuth の確認や審査が必要（Restricted 権限）なので、公開版は手入力のまま
- **完了条件**：テストアカウントで歩数が取れ、RC-1 に「Google Health」と出どころ付きで入る／未接続・拒否・データなしでも全機能が動く／トークンがブラウザに出ない

### RC-9（#15） 3D 地図での案内と 2D への切り替え — 追加

- 今ある `google3d` モード（`app/src/lib/maps.ts` の `Map3DElement`／`Marker3DInteractiveElement`）を Rest Care 用に仕上げる
  - RC-3 の上位候補に順位つきのマーカーを出し、選んだ候補へカメラを寄せる
  - 3D が読み込めない・非対応の地域では、自動で Google 2D（キーなしならモデル地図）に戻して理由を出す
- 3D Maps の表示データから建物の形を取り出して日陰計算に使わない（📄 企画書 14章）。日陰は今の OSM＋太陽位置計算のまま
- 対応地域（みなとみらい）をカバレッジ表で確認。ブラウザ用キーには HTTP リファラー制限、クォータと予算アラートを設定
- **完了条件**：キーありで 3D に候補が順位つきで出る／3D が失敗しても 2D かモデル地図で操作を続けられる

## 7. 進め方 💡

開発期間は 11/10 まで、Regional Day は 11/14 です。中核から順に、各段階で `main` が動く状態を保ちます。

企画書 16章の段階に合わせています。

| 段階 | Issue | 終わったら見せられるもの |
| --- | --- | --- |
| MVP-1 | RC-0 データ ／ RC-2 条件検索 | 冷房・段差なしなどで絞り込める（キーなし・同梱データで完結） |
| MVP-2 | RC-1 入力 ／ RC-3 順位付け ／ RC-4 理由と情報源 ／ RC-7 安全表示 | 入力に応じた上位 3 件と理由、手入力かどうかの表示。**ここで MVP 必須①〜④が揃う** |
| MVP-3 | RC-9 3D 地図 | 3D で候補を案内、失敗時は 2D へ |
| 追加 | RC-6 フィードバック ／ RC-5 休憩のきっかけ | デモシナリオ 6〜7 |
| 挑戦 | RC-8 Google Health 接続 | テストアカウントの歩数が入力に入る |

担当の分け方の例：RC-0（地点データ・現地確認）／RC-1・RC-2（画面）／RC-3（domain とテスト）／RC-4・RC-7（文言・Gemini）／RC-8・RC-9（Google API・サーバー）。

## 8. 完了の定義

- [ ] API キーが全部空の状態で、デモシナリオ 1〜6 が最後まで通る
- [ ] 同じ入力なら同じ順位になる（RC-3 のテスト）
- [ ] 未確認の設備が「利用可能」と表示されない（RC-2, RC-4 のテスト）
- [ ] 予測値・投稿・確認済みデータが画面上で区別され、情報源と更新時刻が出る
- [ ] 疲労感・歩数などの健康に関わる値が、Gemini を含め端末の外へ送られない（RC-8 の集約値の受け取りを除く）
- [ ] 歩数などに「手入力／デモ値／Google Health」の出どころが表示される
- [ ] Google Health 未接続・3D 非対応でも、すべての操作が続けられる
- [ ] Android の APK と iPhone の Safari で、入力→候補→ルート→フィードバックが動く

## 9. 検証と成功指標（企画書 9章）

数値は開発前の想定値を書かず、**学生への試用・現地調査で得た結果だけ** を成果として載せます。

| 確かめること | 測り方 | アプリ側で用意するもの |
| --- | --- | --- |
| 休憩場所を見つけやすくなるか | 既存の探し方（Google マップ等）との時間比較、タスク成功率 | 「休憩する」→ 候補決定までの時間を端末内に記録（任意で書き出し） |
